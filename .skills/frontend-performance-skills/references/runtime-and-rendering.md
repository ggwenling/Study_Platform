# 运行时、渲染与交互

组件代码看着复杂，不等于它就是瓶颈。运行时问题先录下用户真正觉得迟钝的那次操作，再沿主线程时间线往回找。

## 录一段能说明问题的操作

使用生产构建，打开 DevTools Performance 面板。让页面先稳定，再录制一段短而明确的操作，例如打开筛选器、输入一个字符、切换标签页或滚动长列表。长达一分钟、夹杂大量无关动作的 trace 很难判断因果。

记录时说明：

- 操作前页面处于什么状态；
- 用户输入发生在什么时间；
- 下一帧或可见反馈是什么；
- 是否第一次操作才慢；
- 重复几次后变快、变慢还是不变。

## 把慢交互拆开看

INP 对应的交互延迟大体可以分成三段：

1. **输入延迟**：事件已经发生，但主线程还在处理前面的任务。
2. **处理时间**：事件回调和它同步触发的工作正在运行。
3. **呈现延迟**：处理结束后，浏览器还要完成样式、布局、绘制，才能显示下一帧。

输入延迟高时，先找挡在前面的长任务。处理时间高时，进入回调、状态计算和同步工作。呈现延迟高时，看本次更新影响了多大范围的 DOM、样式和绘制。

## 长任务：它挡住了谁

超过 50 ms 的主线程任务值得调查，但不必把每个长任务都消灭。重点是它是否处在加载关键阶段、用户输入之前，或者由常见交互触发。

常见处理方向包括：

- 删除没有用户价值的工作；
- 把大循环或解析拆成可让出主线程的批次；
- 将纯计算移到 Worker，但要计算序列化和通信成本；
- 延后非关键初始化，同时确保不会制造第一次交互的突然等待；
- 减少第三方脚本，或调整它的加载和执行边界。

“放进 `setTimeout`”只是换了排队位置，并不会让工作消失。

## 组件渲染：先看更新传到哪里

React、Vue、Svelte 等框架的细节不同，但诊断思路相近：一次局部状态变化为什么让这么多组件、计算或 DOM 更新？

检查：

- 状态是否放得过高，导致无关子树参与更新；
- context/store 订阅粒度是否过粗；
- 父级在每次渲染中创建的新对象或函数是否破坏了稳定性；
- 派生数据是否重复进行昂贵计算；
- 列表 key 是否稳定，是否造成节点错误复用或重建；
- 隐藏内容是否仍在持续渲染和执行副作用；
- 一次状态更新是否触发同步测量和再次更新。

只有 profiler 显示重复工作有实际成本时，才选择 memoization。缓存本身有比较、内存和认知成本；依赖不稳定时，它可能完全没有收益。

## 大列表和大量 DOM

虚拟化适合视口只展示少量行、总列表很大且节点昂贵的情况。它也会带来滚动定位、可访问性、动态高度和浏览器查找行为上的复杂度。

先考虑是否能分页、减少默认展开内容、让 CSS 跳过屏外渲染，或者只更新发生变化的行。如果确实虚拟化，要测试键盘导航、读屏、搜索、选中状态和动态行高。

## 布局、绘制和合成

如果脚本看起来不重但帧仍然很慢，检查：

- JavaScript 是否在写 DOM 后立刻读布局信息，造成强制同步布局；
- 一次变化是否使很大的 DOM 子树重新计算样式或布局；
- 阴影、模糊、滤镜、大面积透明层是否增加绘制成本；
- 动画是否改变布局属性，能否用 transform/opacity 实现同样效果；
- 合成层是否真正降低工作，还是制造了显存和管理压力。

`will-change` 和合成层都不是默认选项。只给马上要变化、并且 profile 证明值得的元素用。

## 内存增长和用久后变慢

先设计一个重复动作，例如连续进入退出某路由十次、打开关闭弹窗五十次，然后在每一轮之后回到相同的静止状态。观察堆、DOM 节点、监听器和任务是否回落。

常见根因有：

- 事件监听、observer、定时器或订阅没有清理；
- 闭包、全局集合或缓存一直保留旧对象；
- 已移除的 DOM 仍被 JavaScript 引用；
- 请求和异步任务在组件生命周期结束后继续持有状态；
- 图片、canvas、WebGL 或第三方实例没有释放。

一次堆快照里的大对象不是泄漏证明。比较多个相同状态下的快照，并沿 retaining path 找到谁还在持有它。

## 请求瀑布也可能来自运行时代码

组件挂载后才发起请求、请求完成后才发现子组件资源，是常见的站内切换慢原因。沿时间线检查数据、代码和图片能否并行发现，框架是否提供路由级 loader、服务端数据或预取能力。

预取要受网络、用户意图和浪费比例约束。把所有链接都提前请求，可能让真正重要的请求更慢。

## 改完怎么验

保持相同页面状态和操作，比较交互的输入延迟、处理时间、呈现延迟，以及相关任务和渲染范围。功能测试还要覆盖键盘、低端设备、慢网、重复操作和长时间使用。最终再回到 RUM，确认不是只修好了开发者机器上的那一次操作。
