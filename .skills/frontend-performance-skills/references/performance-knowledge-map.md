# 前端性能知识图谱

性能不适合按工具菜单背。顺着体验来更好用：用户看到了什么，哪项指标在描述它，浏览器把时间花在哪一段，接下来该拿什么证据。

## 第一层：用户实际感受到什么

### 内容多久出现

这条线从服务器响应开始，经过 HTML、关键 CSS、字体、图片和 JavaScript，最后落到一次绘制。LCP 是这里最重要的结果指标，TTFB、FCP、资源发现时机和渲染阻塞用来解释它。

### 点击之后多久有反馈

INP 描述交互响应性。分析时要把一次慢交互拆成输入等待、事件处理和浏览器呈现三段，再去找排队的长任务、昂贵的处理函数、过大的渲染范围或同步布局。

### 页面会不会突然跳动

CLS 关心意外布局偏移。没有尺寸的媒体、迟到的内容、字体替换、插入页面上方的提示条都可能造成偏移。修复时要找到具体 shift cluster 和发生移动的元素，而不是只调 CSS 直到分数下降。

### 页面用久了是否依然顺畅

这部分没有一个 Core Web Vital 可以包办。需要看长任务、帧率、内存曲线、事件监听、DOM 数量、后台工作和多次路由切换后的变化。

## 第二层：几个核心指标

下面的阈值用于评价真实用户数据的第 75 百分位。单次本地测量可以作为线索，但不能宣告站点通过了 Core Web Vitals。

| 指标 | 好 | 待改善 | 差 | 最适合回答的问题 |
|---|---:|---:|---:|---|
| LCP | ≤ 2.5 s | 2.5–4.0 s | > 4.0 s | 主要内容什么时候可见 |
| INP | ≤ 200 ms | 200–500 ms | > 500 ms | 用户交互后多久看到下一帧 |
| CLS | ≤ 0.1 | 0.1–0.25 | > 0.25 | 页面在一次访问中有多不稳定 |

### LCP：别只盯着大图

先在 DevTools Performance 面板或 trace 中确认 LCP 元素。然后把耗时拆成服务器响应、资源加载延迟、资源下载时间和元素渲染延迟。LCP 元素即使是图片，真正的问题也可能是它在 JavaScript 执行后才被发现，或者主线程忙到无法及时绘制。

查看位置：PageSpeed Insights/CrUX 看线上分布；DevTools Performance 看本次加载的 LCP 元素和时序；Network 看它何时被发现、何时下载。

### INP：找到最慢的真实交互

INP 不是“页面所有 JavaScript 的耗时”。先记录一次用户会做的操作，找到慢交互，再判断延迟发生在输入等待、事件处理还是呈现阶段。一次初始化长任务可能阻塞后续点击；一次很快的处理函数也可能触发大范围布局和绘制。

查看位置：RUM 用来发现哪种交互、哪类用户经常慢；DevTools Live metrics 和 Performance trace 用来复现并拆解一次交互。

### CLS：找到是谁动了，以及为什么动

CLS 是访问期间布局偏移 session windows 的累计结果。DevTools 的 Layout shifts 轨道能定位偏移簇和相关元素。用户主动操作后紧接着发生的合理变化可能不计入分数，但视觉上仍可能让人不舒服，需要结合现场判断。

查看位置：CrUX/RUM 看真实访问的分布；DevTools Performance 面板查看 shift cluster、移动元素和时间点。

## 第三层：帮你解释指标的信号

- **TTFB**：从请求开始到收到首字节。它混合了重定向、连接、网络和服务器处理时间，不能简单等同于“后端慢”。
- **FCP**：首次绘制文本、图片、非白色 canvas 或 SVG 的时间。它能说明页面开始有内容，但不代表主要内容已经到达。
- **TBT**：Lighthouse 中主线程长任务的实验室指标，常用来排查交互风险。它不是 INP 的线上替代品。
- **Long task**：主线程连续占用超过 50 ms 的任务。它说明可能阻塞输入，但仍要看任务出现的时间和用户操作。
- **资源传输与解压后大小**：网络传输大小影响下载，解压后的 JavaScript 大小更接近解析与编译压力，两者别混为一谈。
- **长帧与渲染耗时**：帮助判断掉帧来自脚本、样式计算、布局、绘制还是合成。
- **内存与 DOM 增长**：适合观察长时间使用、反复导航或打开关闭浮层后有没有对象无法释放。
- **构建时间和阶段 profile**：只回答开发与发布效率，除非构建选择进一步影响了产物。

## 第四层：浏览器的时间花在哪

```text
导航与服务器响应
  → HTML 到达和资源发现
  → DNS / 连接 / 请求 / 缓存
  → CSS 与字体
  → JavaScript 下载、解析、编译、执行
  → 样式计算、布局、绘制、合成
  → 用户交互、状态更新、下一帧
  → 长时间运行后的内存与后台工作
```

一个指标变差，往往是这条链上几个阶段叠加的结果。知识图谱的作用是帮助用户选择下一份证据，而不是从指标直接跳到固定答案。

## 第五层：从指标走到排查路径

| 看到的现象 | 第一个确认动作 | 接下来可能进入 |
|---|---|---|
| LCP 差 | 找到真实 LCP 元素并拆分四段耗时 | TTFB、资源发现、图片/字体、主线程与渲染 |
| INP 差 | 找到具体慢交互和三个延迟阶段 | 长任务、事件处理、状态更新、布局与绘制 |
| CLS 差 | 找到最大 shift cluster 和移动元素 | 媒体尺寸、异步插入、字体、动画 |
| 首屏 JS 很大 | 按路由查看 chunk 和模块组成 | 依赖、导入方式、拆包、目标环境 |
| 切页后越来越卡 | 重复关键操作并观察内存和监听器 | 泄漏、未清理副作用、缓存无界增长 |
| 构建变慢 | 对比版本并拿到阶段 profile | 插件、转换范围、缓存、类型检查、source map |
| 只在部分用户中慢 | 按设备、网络、路由和版本切分 RUM | 分群后的具体瓶颈 |

## 第六层：什么时候算优化完成

性能改动至少要回答三个问题：目标指标是否改善，重要功能是否保持正确，成本是否被转移到了别处。比如延迟加载能减轻首屏，也可能让第一次交互多一次等待；激进拆包能减少单个 chunk，也可能制造请求瀑布；缓存能让回访更快，也可能让版本更新更复杂。

真正完整的闭环是：现场指标发现问题，实验室工具定位原因，小改动验证假设，发布后再用现场数据确认用户得到了改善。
