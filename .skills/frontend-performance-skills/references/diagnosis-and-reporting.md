# 从线索走到结论

性能报告不必把所有可能性罗列一遍。读完的人应该能知道：眼下最可信的瓶颈是什么、为什么先处理它，以及怎么验收改动。

## 先把现场写清楚

开头几句话交代现场：

- 关键页面和用户动作；
- 构建版本与运行环境；
- 设备、网络、浏览器和缓存状态；
- 使用了哪些 field 或 lab 数据；
- 哪些环境或用户群还没有覆盖。

这一步不花时间，却能避免把本机一次冷启动误写成线上结论。

## 先找卡在哪一段

先判断主要时间花在什么地方，再钻到文件和代码：

1. **服务器与导航**：TTFB、重定向、连接或后端生成时间占了大头。
2. **资源发现与传输**：关键资源出现得晚、请求串行、没有命中缓存或传输体积过大。
3. **JavaScript 主线程**：解析、执行、长任务或第三方代码阻塞了加载和交互。
4. **样式与渲染**：样式计算、布局、绘制、合成或布局抖动消耗明显。
5. **长期运行**：内存、监听器、计时器、缓存或 DOM 随操作持续增长。
6. **构建阶段**：某个 loader、插件、类型检查、source map 或转换范围拖慢反馈。

两个阶段都重时，顺手写出它们的关系。比如 LCP 图片发现得晚，网络开始晚和 LCP 变差其实是一件事，别拆成两条互不相干的收益。

## 每条结论都要经得起追问

每个 finding 最少包含下面几项：

```text
发现：产品详情页的 LCP 图片要等到客户端接口返回后才进入请求队列。
证据：trace 中图片请求在导航后 1.8 s 才开始；LCP 元素就是该图片。
影响：移动端首次访问的主要内容显示被直接推迟。
置信度：高。
建议：让初始 HTML 提供图片 URL，或在确定 URL 时用合适的 preload 提前发现。
风险：preload 错误图片会争抢带宽；响应式图片需要匹配实际候选。
验证：同一测试条件下比较图片请求开始时间、LCP 四阶段和最终 LCP。
```

“发现”说发生了什么，“证据”说明为什么相信它，“建议”才讨论怎么改。源码里的可疑写法如果没有运行数据支撑，应写成“风险”或“待验证假设”。

## 如何排优先级

不要仅凭体积或耗时大小排序。综合考虑：

- **用户影响**：是否命中重要路径和大量用户；
- **证据强度**：是否在 field data、trace 或产物中直接看到；
- **预期收益**：改动是否作用在当前限制阶段；
- **工程成本**：实现、联调、迁移和维护的代价；
- **回归风险**：正确性、缓存、加载顺序、兼容性和可访问性风险。

可以使用下面的朴素分级，但要解释为什么：

- **P0**：重要路径正在受到明显影响，证据直接，应该先处理。
- **P1**：影响可观、证据较强，但范围、成本或风险需要权衡。
- **P2**：结构性债务、较小收益，或仍需补证据。

不要伪造精确的收益数字。没有 A/B、前后实验或足够数据时，写“预计改善资源发现时间”比写“LCP 将降低 37%”诚实得多。

## 建议的报告骨架

```markdown
# 性能调查结论

## 这次看了什么
页面、操作、环境、数据来源和限制。

## 最重要的判断
用一段话说明主要限制阶段和最有价值的下一步。

## P0 / P1 / P2 发现
每项包含：发现、证据、影响、置信度、建议、风险、验证。

## 还缺什么证据
只列会改变当前判断的材料，并给出获取方法。

## 验证方案
写清前后条件、观察指标、重复次数和发布后的 field data 观察窗口。
```

写完后回头问三件事：别人能否根据证据挑战这条结论？知道先改哪里吗？改完能判断成败吗？三个答案都是“不能”，它大概率还只是建议清单。
