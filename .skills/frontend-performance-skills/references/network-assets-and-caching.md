# 网络、资源与缓存

加载性能不等于把所有文件压到最小。关键是当前页面需要的内容能早发现、能并行传输、能及时渲染；回访时也别重复做没必要的工作。

## 先把请求瀑布读明白

使用生产构建，分别记录冷缓存和正常缓存下的关键路径。顺着时间线回答：

- 文档请求是否有重定向，TTFB 花在哪里；
- LCP 资源什么时候被发现，谁发现了它；
- CSS、字体、脚本和接口之间是否形成串行链；
- 哪些资源阻塞渲染或占用了早期带宽；
- HTTP 缓存、service worker、CDN 是否命中；
- 第三方域名的连接和脚本执行是否挤占关键路径；
- 重复访问时，哪些本应复用的内容又下载了一遍。

Network 面板的 Initiator 和 Timing 很有用。HAR 适合分享请求级证据，但通常不包含完整的 JavaScript 和渲染因果链。

当调查 DNS、TCP/TLS、重定向、HTTPS、跨域 origin、CDN 或第三方连接时，再读取 [network-transport-and-domains.md](network-transport-and-domains.md)。

## TTFB 不只是后端执行时间

TTFB 可以包含重定向、DNS、连接、TLS、网络往返、CDN 等待和源站处理。先用 Timing、服务器日志或 CDN 指标拆开，再决定是缓存、网络还是服务端渲染问题。

如果 HTML 是按用户动态生成的，缓存策略要服从正确性和隐私边界。不要为了一个更低的 TTFB 把用户专属内容错误地共享出去。

## 关键资源要早点被浏览器看见

浏览器越早从 HTML 或 CSS 中看到资源，越有机会并行加载。由客户端渲染或接口响应拼出的 LCP 图片，往往发现得太晚。

优化候选包括：

- 让关键内容和资源 URL 出现在初始 HTML；
- 正确设置资源优先级；
- 对确定且关键的资源使用 preload；
- 对可预测的下一步使用有节制的 prefetch；
- 避免先加载脚本、执行脚本，再由脚本发现关键资源的链条。

preload 是对浏览器调度的强提示。URL、`as`、CORS 或响应式图片候选不匹配时，可能重复下载或浪费带宽。每次添加后都看瀑布，而不是看到关键资源就批量 preload。

## 图片

先找页面真正显示的尺寸、设备像素比和内容类型，再讨论格式：

- 使用 `srcset` / `sizes` 或框架图片能力提供合适候选；
- 为图片预留宽高或 aspect ratio，避免布局偏移；
- 首屏 LCP 图片通常不应懒加载；
- 屏外图片可以懒加载，但注意快速滚动和轮播场景；
- 比较视觉质量后再选择 AVIF、WebP 或其他编码；
- 避免用远大于显示区域的原图承担响应式工作。

图片 CDN 能解决转换和尺寸分发，但 URL 稳定性、缓存键、成本和降级也要考虑。

## 字体

字体问题通常同时影响请求、文本出现和布局稳定性。检查字符集、字重数量、unicode-range、跨域设置、缓存和 `font-display`。

子集化和减少字重往往有效，但不能删掉真实内容需要的字符。`font-display` 的选择是品牌、可读性和布局之间的取舍；确认 fallback 字体的度量差异，必要时使用字体度量覆盖减少偏移。

只 preload 当前页面必用的字体文件。预加载每一种字重会与更重要的资源争抢带宽。

## JavaScript 与 CSS 的加载

脚本的成本包括下载、解压、解析、编译和执行。`async`、`defer`、module、动态导入各自改变顺序和依赖关系，修改前先确认脚本是否依赖 DOM 或其他脚本。

CSS 是否阻塞渲染取决于 media、引用方式和使用位置。拆出关键 CSS 可能加快首次绘制，也可能增加 HTML、重复样式或缓存复杂度。以 trace 和产物验证，不要把一套内联方案复制到所有页面。

## HTTP 缓存和内容寻址

通常可以把资源分成两类：

- 带内容哈希、URL 随内容变化的静态资源，适合长时间 immutable 缓存；
- HTML、接口和不带版本的资源，需要根据更新与正确性设计 revalidation 或较短 TTL。

检查 `Cache-Control`、ETag/Last-Modified、Vary、CDN cache key 和 service worker 行为是否一致。一个文件显示 `(disk cache)` 不代表所有用户和边缘节点都能正确命中。

缓存改动要测试发布、回滚和多版本并存。旧 HTML 引用的新资源、或新 HTML 引用已删除的旧资源，都是需要设计的失败模式。

## 第三方脚本

统计每个第三方的网络体积、主线程时间、加载阶段和业务用途。可以延后、按同意状态或用户意图加载，也可以删除没有实际使用的集成。但埋点、风控、支付和客服常有业务约束，先确认负责人和数据要求。

第三方域名的 `preconnect` 只对较早且确定的连接有价值。过多预连接会占用 socket 和握手资源。

## 验证时盯什么

保持测试条件一致，比较关键资源的发现时间、请求开始时间、优先级、传输大小、缓存命中和最终渲染。冷缓存验证新访客路径，热缓存验证回访和站内导航。发布后再用 field data 检查不同设备与网络分组，避免只改善了办公室宽带。
