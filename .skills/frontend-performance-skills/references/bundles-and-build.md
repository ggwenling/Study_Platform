# 包、引用与构建性能

包体问题很容易被一个醒目的数字带偏。真正该问的是：哪批用户在哪条路由下载、解析、执行了什么，它为什么会出现在那里。构建慢是另一条线，得用单独的耗时证据看。

## 刚接手项目时先看什么

先确认项目实际使用的工具，不要根据几个文件名猜整套架构：

- package manager、lockfile 和 workspace 布局；
- 框架、构建器及生产构建命令；
- 浏览器目标、转译与 polyfill 策略；
- SSR、SSG、CSR 或混合渲染方式；
- 路由边界和动态导入位置；
- 是否已有 bundle stats、可视化报告或构建 profile。

可以运行 [collect-project-context.mjs](../scripts/collect-project-context.mjs) 建立目录级上下文，但它只列线索。依赖出现在 `package.json` 中，不代表它进入了用户的首屏代码。

当问题涉及依赖去重、重复实现/引用、生产构建产物、缓存响应头或 source map 发布策略时，再读取 [dependency-and-delivery-controls.md](dependency-and-delivery-controls.md)。

## 包体：沿路由和 chunk 往下查

优先使用项目已有的分析命令或构建器产出的 stats。安装新的 bundle analyzer 会改动依赖或配置，除非用户已经要求实施，否则先说明需要它解决什么问题。

分析时同时看：

- 首次进入目标路由要下载哪些入口和共享 chunk；
- 压缩传输大小与解压后大小；
- 代码在什么时机执行，而不只是何时下载；
- 重复模块或同一库的多个版本；
- 大型模块由哪条 import 链带入；
- 动态 chunk 是否形成新的请求瀑布；
- chunk 命名和内容是否利于长期缓存。

一个后台管理路由里的大编辑器通常不影响营销首页。一个不大的同步初始化模块，却可能因为执行时机而伤害 INP。报告里要把模块大小和用户影响连起来。

## 常见的引用问题

### 聚合导出扩大了模块边界

`index.ts` 这类 barrel file 让调用端更整洁，但也可能把初始化副作用、CSS 或构建器无法裁剪的模块带进来。先沿产物或模块图证明引用链，再考虑改为更窄的子路径导入。

不要全仓机械替换聚合导入。有些库的 `exports` 和 tree-shaking 做得很好，改写只会降低可维护性而没有产物收益。

### CommonJS、动态访问与副作用阻碍 tree-shaking

检查发布包格式、`sideEffects` 声明、顶层副作用、动态属性访问以及构建器对模块的理解。修改 `sideEffects` 属于高风险动作：错误标记可能让必要的 CSS、注册代码或初始化逻辑从生产包消失。必须用生产构建和功能测试验证。

### 一个依赖出现了多个版本

先用对应 package manager 的依赖树解释版本来源，再决定升级、对齐、override 或 dedupe。强制锁到单一版本可能突破库声明的兼容范围，不能只为了报告里的重复模块变成零。

### 整库引入，而页面只用一小部分

确认库是否提供稳定的子路径或按需 API。导入内部私有路径看似能省体积，却可能在小版本升级时破坏。优先使用包公开的 `exports`。

### 类型依赖或开发工具意外进入运行时

检查 import 是否仅用于类型、代码生成产物是否混入工具本身、服务端专用模块是否跨过客户端边界。这类问题往往比通用的压缩建议更值得先修。

## 代码拆分别切得太碎

拆分的目的是让代码接近使用时机，同时保留合理的缓存与请求并行度。判断一个边界是否合适时，看：

- 这段功能是否不在首屏或并非每个用户都使用；
- 触发后是否允许等待，能否在空闲或意图出现时预取；
- 它与入口共享多少依赖；
- 拆分后会不会先请求组件，再请求数据，再请求内部 chunk；
- 发布后共享 chunk 的变化是否让缓存更容易失效。

路由、重型编辑器、图表、地图和管理功能通常是候选，但仍以真实路径和产物为准。

## 浏览器目标、转译与 polyfill

过旧的目标环境可能带来更多语法转换和 polyfill；过新的目标可能丢掉真实用户。先检查项目支持范围、用户浏览器分布和业务承诺，再调整 Browserslist 或构建 target。

如果现代与旧版构建并存，要比较真实流量收益和发布复杂度。不要为了少量体积擅自放弃兼容范围。

## 构建慢，先拿阶段耗时

使用同一机器、同一 Node 版本和可比的冷/热缓存条件记录构建。关注：

- 模块解析、转译、类型检查、CSS、压缩、source map 各阶段时间；
- 插件/loader 的调用次数和输入范围；
- monorepo 中被错误扩大了的依赖图；
- 缓存命中率和缓存失效原因；
- 构建前后的代码生成、复制、上传任务；
- 峰值内存和垃圾回收是否成为瓶颈。

常见修复包括缩小转换范围、让类型检查和打包合理并行、修缓存键、减少重复插件工作、升级已知有性能问题的工具版本。每一项都要能在 profile 里找到对应时间，别只因为“大家都这么配”。

## 交付时至少给出

- 目标路由、构建模式和产物来源；
- 模块或阶段为什么会成为瓶颈；
- 引用链、chunk 或 profile 中的证据；
- 修复会改变下载、执行、缓存还是构建反馈；
- 对兼容性、加载时序和功能正确性的风险；
- 生产构建前后怎样对比。
