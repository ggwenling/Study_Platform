# 验证优化与防止回归

性能改动最容易停在“代码看起来更合理”。真正算完成，是同一条用户路径在可比条件下变好了，也没有把成本转给交互、缓存、正确性或另一类用户。

## 动手前先写一句验证假设

动手前，用一句话说明改动应该影响哪段时间：

```text
把商品主图 URL 放进服务端 HTML，应该让图片请求更早开始，从而缩短 LCP 的资源加载延迟；它不一定改变图片下载时长。
```

这句话决定该看哪些数据。没有假设时，人很容易只比较一个总分，并把任何波动都算成成功。

## 本地前后怎么比

尽量固定：

- 同一台设备与浏览器版本；
- 同一种生产构建；
- 同一页面数据与用户状态；
- 相同的网络和 CPU 模拟；
- 同样的冷缓存或热缓存条件；
- 同一段操作与录制范围。

性能数据有噪声。跑多次并保留原始结果，看中位水平和离散程度，不要只挑最好的一次。如果机器后台负载明显变化，重新采集比解释异常值更可靠。

不同问题对应不同验证信号：

| 改动 | 直接信号 | 还要防什么 |
|---|---|---|
| 提前发现 LCP 资源 | 请求开始时间、LCP 四阶段 | 带宽争抢、重复 preload |
| 拆分非关键 JavaScript | 入口下载/执行时间、目标路由 chunk | 第一次使用等待、请求瀑布 |
| 缩小组件更新范围 | interaction trace、渲染组件数、呈现延迟 | 状态不同步、缓存成本 |
| 修复内存泄漏 | 重复操作后的 retained objects 和堆趋势 | 功能清理过早、异步竞态 |
| 调整缓存 | 冷/热缓存瀑布、命中和 revalidation | 发布与回滚、多版本资源 |
| 优化构建 | 同条件阶段 profile、总时长、峰值内存 | 产物差异、缓存正确性 |

## 真正的用户收益，要看 field data

本地结果证明“这项改动在某个受控条件下有效”。发布后使用 RUM 或 CrUX 观察目标页面、设备和版本，才知道用户分布是否改善。

自建 RUM 可以在发布后较快按版本观察；CrUX/PageSpeed 是滚动聚合数据，变化显现得更慢，也可能受流量组成影响。不要在发布第二天因为 CrUX 没变就宣布失败。

判断 Core Web Vitals 时看第 75 百分位以及达到 good threshold 的访问比例。业务也可能更关心慢设备、核心地区或付费路径的尾部表现，这时应保留额外分组，而不是只维护一个全站数字。

## 预算要跟产品路径走

预算的作用是阻止明确的回归，不是把所有页面塞进同一组数字。可以为不同页面模板建立：

- Core Web Vitals field 目标；
- 关键路由的 JavaScript/CSS/图片传输与解压后体积；
- 主线程阻塞、关键请求数或第三方预算；
- 构建时间、开发冷启动或 HMR 反馈预算。

先从当前基线和业务目标制定一个能执行的门槛，再逐步收紧。完全脱离现状的理想数字，通常只会让团队关闭检查。

## 哪些指标适合在 CI 里卡住

稳定、确定性较高的项目适合硬失败，例如：

- 某个入口或路由产物超过约定体积；
- 出现禁止进入客户端的包；
- 依赖重复或 chunk 数量超过明确边界；
- Lighthouse 的某条确定性审计失败。

容易受机器和网络波动影响的时间指标，更适合多次运行、容忍区间或趋势告警。若要用 Lighthouse CI，固定页面数据和运行环境，并保存报告方便追踪原因。

## 回归时，别把线索丢了

每次性能数据至少带上版本、页面模板、设备类别和采集方式。构建产物报告也应能与 commit 或发布版本对应。没有版本维度的图表只能说明“最近变慢了”，却很难帮人找到是哪次改动。

## 完成前的最后检查

- 目标用户路径真的改善了吗？
- 对照条件一致，原始证据还在吗？
- 功能、可访问性和兼容性通过了吗？
- 成本是否转移到首次交互、其他路由、低端设备或回访用户？
- 发布后由谁、用什么数据、观察多久？
- 如果结果变差，回滚点是什么？
