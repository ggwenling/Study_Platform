## 真实链路

使用随机新建、名称以 `_test` 结尾的隔离数据库及 `.local/closure/storage`，启动独立 API、worker 和 Web；模型为 `deepseek-flash` 与 `qwen3.7-text-embedding-flash`（1024 维）。使用了真实模型调用，不能据这些少量样例推导整体准确率。

| 场景 | 结果与证据范围 |
| --- | --- |
| TXT、DOCX、PNG、JPEG、扫描 PDF | 实际处理完成，资料可问答 |
| 空白图片、损坏 DOCX | 进入失败状态，没有空内容假就绪 |
| 图片及扫描 PDF 的 OCR | 测试文字中的 `QZ-731` 可读，鉴权原页接口返回 200 |
| 固定中文资料问答 | 温度上限 17、交付日期 12 月 18 日、OCR 柜号均答出并附实际来源，来源读取可用 |
| 同会话 A → B | B 轮未复用 A 的唯一事实，明确资料不足 |
| 指定本地 DOCX | 实际导入；数据库、三层架构与存储引擎问题得到有对应资料支持的结果；检索未覆盖的技术细节明确说明依据不足 |
| 30 份资料 | 全部处理就绪；跨分页读取后共 30 份，无遗漏 |
| 生成中强杀 API | 重启后保留已保存的部分回答；在隔离库将该轮租约设为过期，重访收敛失败 |
| 显式重试中断轮次 | 复用原 turn，仍只有原来的两条消息，最终完成 |

指定 OneDrive 目录仅使用本地已可读的 DOCX，未批量读取云端占位文件。原文件保持不变。私人正文、回答原文、测试账户及原始运行日志仅在忽略提交的 `.local/closure`，不进入仓库。

补充测试时发现两个验收 worker 共用队列但存储目录不一致，导致一批隔离测试任务失败；统一配置并串行执行后，显式重试及 30 份资料验收通过。此过程未操作开发库或已有其他数据库。

## 浏览器与启停

通过 agent-browser 操作真实页面，完成无库登录、保留草稿页内建库、上传、状态就绪、发送问题、引用弹窗、空白图失败、显式重试、图片上传。注入仅作用于资料读取的 fetch 故障，确认保留上次结果、显示尚未确认并可手动恢复。

检查桌面 1440×900、窄屏 390×844 与 320×740。当前库资料默认收起，上传时展开；长库名和失败信息可换行，资料列表内部滚动。所测窄屏无页面横向溢出，发送、展开和重试可达。这是 Chromium 视口模拟，未作实体手机或软键盘验收。

启停工具以相同控制逻辑、隔离测试端口完成真实的启动 → 状态 → 再次启动 → 停止，使用 venv Python 和 Node；验证 Windows Python 包装进程的实际监听子进程归属。默认端口存在原手动服务时，启动器实际报告冲突，没有终止它们。测试结束停止本轮进程并删除新建验收数据库，原开发服务和 PostgreSQL 保持运行。

## 仍然存在的边界

- API ready 不验证模型余额、不判断 worker 是否卡住；启动器状态检测的是受管理进程存活，没有增加持久心跳或自动监护。
- 强制退出允许丢失最后一次保存后的少量流式内容；恢复不是逐 token 续传。
- OCR 验收使用清晰印刷文字，不代表图表、复杂公式、手写或模糊图片理解能力。
- 本轮未改变检索算法，没有混合检索优越性或大规模吞吐结论。
- 手动备份恢复独立后续实施；当前持久化不构成备份。
- 设置、完整资料管理、更多摘要交互及其余 P0 场景仍需独立验收。
